## 二、为什么 akshare 的新闻接口只有一个是可用的

实测（这是最初以为"没有历史新闻"的原因）：

| 接口 | 支持按日期检索 |
|---|---|
| `ak.news_cctv` | ✅ **唯一支持** |
| `ak.stock_info_global_em` / `_cls` / `_ths` / `_sina` / `_futu` | ❌ 只返回最新几条 |
| `ak.stock_news_em` | ❌ 只回溯约 1 个月 |
| `ak.stock_news_main_cx`（财新） | ❌ 只有最新 100 条 |
| `ak.news_economic_baidu` | ❌ 需要百度 cookie，实测失败 |

**教训：akshare 封装的是"常用接口"，不代表数据源穷尽。直接测原始站点才找到出路。**

## 三、各源详情

### 3.1 新浪历史首页（覆盖最广，推荐主用）

```
https://finance.sina.com.cn/head/finance{YYYYMMDD}am.shtml
```

实测覆盖：2010-01-01 ✅、2013-01-01 ✅、2015-06-20 ✅、2018-01-01 ✅、
2023-01-01 ✅、2025-01-01 ✅、2026-09-23 ✅

**内容质量**（以 2020-02-03 早间为例，抽出 212 条正文标题，其中 59 条疫情相关）：

```
· 管涛：新冠肺炎将对人民币汇率走势产生阶段性冲击
· 国泰:理性看待疫情 对市场冲击有限
· 股指 短期存在调整需求
· 假期国内外重要数据与事件梳理 期货市场最全投资攻略
```

**这正是游戏要的"线索"**：真实、有信息量、但同一天既有"冲击有限"也有"调整需求"——
不直接给答案，玩家得自己判断。

**两个工程坑**：
1. **传输会截断**（`IncompleteRead`）——必须捕获异常并取 `e.partial`，再重试
2. **文章 URL 格式随年代变化** —— 按日期过滤的正则对不同年份要调整
3. 页面含导航/广告，需过滤（关键词黑名单：开户/下载/客户端/意见反馈）

### 3.2 新闻联播文字稿

`ak.news_cctv(date="YYYYMMDD")`，覆盖 2016-06 至今（2016-01 返回 0 条）。

- 慢：**34 秒/天**（逐条抓取，12 条左右）
- 内容是官方政策播报，**偏宏观**
- 价值：政策信号。对"政策市"特征的 A 股是真实线索

**实测验证过它的线索价值**：2020-02-03（疫情后开盘 −11.23%）的前 4 个交易日：

```
2020-01-20  习近平对新型冠状病毒感染的肺炎疫情作出重要指示
2020-01-21  我国全力应对新型冠状病毒感染的肺炎疫情
2020-01-22  我国累计报告确诊病例 440 例
2020-01-23  累计报告确诊病例 571 例 + 世卫组织肯定中国防控措施
```

风险是**逐步升级**的，玩家读得出来。且 01-23 是春节前最后交易日，
之后休市到 02-03 —— **玩家明知有风险却卖不掉**，这是 A 股最真实的体验。

### 3.3 证券时报电子报

```
https://epaper.stcn.com/paper/zqsb/html/{YYYY-MM}/{DD}/node_2.htm
```

实测：2017（491 篇）、2018（477）、2019（157）、2020（528）、2021（437）、2022（363）
→ **覆盖 2017–2022**；2023 以后只有 1KB（0 篇）；2015/2016 连接失败或截断。

- **CORS `*`**（浏览器可直连，但离线批量抓取更合适）
- 内容是真正的财经报道（"华泰证券研究所所长陆挺:两地融通打造一体化管理平台"）
- 同样有截断问题

### 3.4 证券日报电子报

```
http://epaper.zqrb.cn/html/{YYYY-MM}/{DD}/node_2.htm
```

实测：2020（473 篇）、2022（240）、2023（204）、2024（324）
→ **覆盖 2020–2024**；2016–2018 返回 HTTPError。

与证券时报**时段互补**。

## 四、离线批量抓取方案

游戏是纯前端静态站，历史新闻**必须预先抓取并打包**。工程要点：

1. **容错抓取器**（必需）：
   ```python
   try:
       raw = resp.read()
   except http.client.IncompleteRead as e:
       raw = e.partial      # 截断时取已读部分，别丢弃
   ```
   所有电子报站点都出现过截断，不容错会丢大量数据。

2. **节流**：单站点串行 + 1~2 秒间隔，避免被封。实测这些站点对低频抓取友好。

3. **只抓标题 + 摘要**，不抓全文 —— 体积和版权考虑（见下）。

4. **按关卡需求抓取**，不抓全量：一局 30 个交易日 × 10 关 = 300 天，
   比抓 16 年全量（约 5800 天）省 95% 的工作量。

5. **增量更新**：新闻库随时间积累，每天补当天即可。

## 六、关键词匹配：错在哪、怎么修的

新闻面板要把「和持仓可能相关的新闻」挑出来。挑的办法是**关键词匹配**——把股票名或代码
在标题+摘要里找一遍。中文没有词边界，`text.includes(name)` 等于把「这四个字出现过」
当成「在说这家公司」。这一节记录**实测**出来的误差，以及修法。

### 怎么量的

`scripts/audit-news-match.ts`：拿快照里的 **619 个真实股票名** × 真实快讯跑一遍，
打印命中股票数、名字互为子串的股票对、每处命中的左右上下文，以及只靠数字命中的。
语料用同花顺端点翻页抓（`AUDIT_PAGES=16` → **800 条头条**，
详见第四节：翻页要带浏览器头，否则拿到非 JSON）。

**先量再改的理由**：凭想象改匹配规则最容易越改越糟 —— 收紧一条规则，
同时误伤多少真命中是看不见的；只有把「改之前命中哪些、改之后命中哪些」逐只列出来，
才知道这次改动到底对不对。

### 实测结论

改之前命中 **89 只**股票；改之后 **85 只**；**新增命中 0 只**。被挡掉的 4 只逐条核对如下：

| 股票 | 头条 | 实际说的是 |
| --- | --- | --- |
| 中国银行 601988 | 6月末我国**银行业**对外金融资产21443亿美元 | 全行业数据（外汇管理局） |
| 上海银行 601229 | **上海银行间**同业拆放利率(Shibor)多数下跌 | Shibor 利率 |
| 中国石油 601857 | 贝莱德对**中国石油化工**股份的多头持仓增至7.16% | 中国石化 600028 的 H 股 |
| 中信金属 601061 | 受理号为 CXSL**2601061**、CXSL2601062 | 药品受理号，不是股票代码 |

四条全是误命中，没有一条是真命中被冤枉。**误命中只有一种形状：名字后面接着几个字，
凑成了另一个词**（外加一条数字边界问题）。

另外两条**没被证实**的旧猜测，一并记下以免以后再当依据：

- 「中国平安会误匹配中国平安银行」——**不成立**。619 只股票里，名字互为子串的一对都没有。
  脚本每次都会打印这张表，将来快照里真出现了会立刻看见。
- 「名字后面跟了中文字就算可疑」——**判据错了**。`中国银行` + `业` 是误命中，
  但 `万科A` + `业绩预告` 说的是万科 A 自己；`宁德时代` + `长期` 也是真命中。
  所以只能比**完整的词**，不能比单个字。

### 修法

1. **泛词吞并**：维护一张完整的词表，命中位置与表里某个词**重叠**即判为非命中。
   「重叠」的判据是词的起点落在 `[命中起点, 命中起点 + 名字长度)` 区间内，这样两类都盖得住：

   - 名字 + 完整词：`中国银行` + `业` → 词「银行业」从命中起点开始
   - 名字的尾巴 + 词：`上海银` + `行间` → 词「银行间」从起点后两格开始

   同一个词出现在名字**后面很远**的地方（「中国银行发布公告，银行业整体承压」）不算重叠，
   名字照常命中。词表在 `packages/data/src/news.ts` 的 `GENERIC_PHRASES`。

2. **数字边界**：6 位代码用 `(?<!\d)601061(?!\d)` 匹配，`CXSL2601061` 这种就不会命中。

新增误命中时：加进 `GENERIC_PHRASES`，并在 `packages/data/src/news.test.ts` 补一条用例。

### 残留的已知误差

- `中国石化` 与 `中国石油` 只靠「化工」二字区分；标题若写成「中国石化行业」，
  仍可能被算到某只股票头上。这类只能靠持续加词表，做不到零误差。
- 匹配**只决定「给不给你看」**，不决定利好利空 —— 面板上写的就是「可能相关」。
  引擎的四层漏斗与个股分类完全不读新闻，新闻不会影响任何判断。

## 七、重复新闻：先数了一遍，再去重

「要不要合并重复新闻」听起来像是个必要功能。动手前先抓 1000 条真实快讯
（同花顺 20 页 × 50 条）数了一下：

| 重复的形状 | 实测数量 |
| --- | --- |
| 同一 `id` 出现两次 | **0 条** |
| 标题完全相同（抹掉标点与空白后） | **2 组 4 条（0.2%）** |
| 一条标题包含另一条 | 1 对 —— 而且是**两条不同的新闻** |
| `digest` 与 `title` 一模一样 | 33 条（3.3%） |

结论：**刷屏并不存在**。真正需要处理的只有三件事，都不是「合并同类项」那种大工程。

**做**：`dedupeNews(items)`（`packages/data/src/news.ts`）按 id 与归一化标题去重，
保留每组里最新的一条。接在 `fetchLatestNews` 里，所有消费者自动受益。
两个 provider 因此多要 `DEDUPE_HEADROOM = 10` 条，免得「碰巧撞上一条重复，列表就少一条」。

**不做**：按「一条标题包含另一条」合并。实测 1000 条里只有 1 对这种形状，
而且它长这样：

```
  中国贸促会2026年APEC工商领导人峰会筹备工作进展顺利
  2026年APEC工商领导人峰会筹备工作进展顺利
```

这是两条不同的新闻。按包含关系合并，等于凭空删掉一条真新闻 —— 风险远大于收益。

**已经在 UI 里处理的**：第 4 行那 33 条 `digest === title`。
`NewsPanel.tsx` 的判断是 `item.digest.length > 0 && item.digest !== item.title`，
摘要和标题一样时不给「展开」按钮，不会把同一句话显示两遍。

一句话：**先量，再决定要不要写**。这一节的价值不在那段去重代码（十几行），
而在于它避免了写一套「相似度合并」然后删掉真新闻。
